# Rules for work on review-lesson-java-kotlin

How lessons and docs are written in this repo (the "docs pattern"). Details and the lesson list live in
[`kotlin-review/README.md`](../../kotlin-review/README.md) and [`java-review/README.md`](../../java-review/README.md) (§ Folder convention, § Lesson plan); this file is the short rule set.
Rules 1-13 are written for the Kotlin module; the Java module follows them with the substitutions of rules 14-17, the TypeScript module with those of rules 18-21.

## Lessons

1. **Write the lessons the owner names, no more.** Default pace is one lesson at a time on the owner's mark, never ahead of the plan. When the owner names several in one message ("array/list and set/map/stack"), map each to its lesson number in the plan and write one folder per named lesson. When the owner asks for the full set ("full lesson"), write every lesson still marked ⬜ in the plan, in plan order, one folder per lesson.
2. **Lesson folder** = `kotlin-review/src/main/kotlin/review/<number>-<kebab-case-name>/`, numbered from 0 as in the README lesson plan (`0-primitive-data-type`). Create the folder only when that lesson is written.
3. **One topic per file**, never a whole lesson in one file. Each file has its own `main()` and a KDoc header with its title and a `Run:` line.
4. **Package** = the lesson name without its number (`0-primitive-data-type` -> `package review.primitive`). Folder and package differ on purpose. The run class is `<package>.<FileName>Kt`, unless the file carries `@file:JvmName("X")` (then `<package>.X`, as `FileFacade.kt` in lesson 16 does on purpose). Top-level functions in a lesson file are public in that package, so keep their names unique within it (`twoSum` is in `review.sets`, `twoSumBrute` in `review.loops`).
5. **Lessons are numbered from 0 and priority-marked** (🔴 Must · 🟡 Should · ⚪ Nice) in the README lesson plan. When a lesson is written, set its Status in that table, list its files in the README `Files of lesson N` line, and when the plan row covers more than its title said (stack and heap went into lesson 5), reword the row; when the plan changes, keep numbers, folders and the "live-coding / Q&A" ranges consistent.

## Printing

6. **Write the syntax as plain Kotlin, never inside a quoted string.** One real line of code per demo: `val i = 42;  show { i }  // type inferred: Int` for a declaration, `show { 7 / 2 }  // Int / Int truncates` for an expression. No `show("7 / 2", 7 / 2, "note")` style: the code must not be typed twice.
7. **How `show { }` works:** it prints the code text and the trailing `// comment` of its own source line, read back from the lesson file at run time, plus the real value and its type. So a `show` call stays on ONE line, `show { ... }` is the last statement on it, and the note is its `// comment`. Whatever comes before `show` on the line is printed as the code, so it must be the statement that produces the shown value: `val i = 42;  show { i }` is fine, but a setup statement followed by `show { other.poll() }` prints the wrong code, so put the setup on its own line.
   To show what a loop visits, collect it in one line, `show { buildList { for (i in 1..5) add(i) } }`; a longer loop (labels, nested) goes in plain code above, then `show { result }`.
8. **Name the syntax:** start each section that introduces syntax with `syntax("val name: Type = value" to "explicit type", ...)`, the template written with placeholders. Use `wontCompile(code, why)` for code the compiler rejects (confirm every claim with a scratch compile first), `note()` for a rule or an exception, `block(text)` for a multi-line text such as pretty-printed JSON, `bigO("operation" to "O(...)", ...)` for the cost of the operations a data-structure lesson teaches, `title()` once per file and `section()` per group. All print through `review.Output` (`kotlin-review/src/main/kotlin/review/Output.kt`); no bare `println` for results.
9. **Keep both output modes working:** the colored and box-line default, and plain ASCII (`-Dstyle=plain` or `NO_COLOR`), so keep strings given to `syntax`, `note` and `wontCompile` ASCII-only. Never put a raw control character, or a backslash-u escape of one, in a source file: `Output.kt` builds the ESC character at run time (`27.toChar()`).

## Content

10. **Teach the interview traps:** every lesson shows the surprise an interviewer likes (overflow, `0.1 + 0.2`, integer division, `1..0` is empty, `all {}` on an empty list ...), with the real value printed.
11. **Show the cost:** a lesson that teaches a data structure or a loop pattern ends with a `Cost` section (`bigO(...)`), because complexity is what coding interviews ask about.
12. **Verify before saying done:** compile and run every file of the lesson with `mvn -q compile exec:java -Dmain.class=<package>.<FileName>Kt` and check the printed values against the notes. After any change to `Output.kt` (it is shared by every lesson), re-run at least one file of each lesson. When several lessons are written in parallel, each writer builds in its own copy of the module and copies the finished folder into the repo; Maven runs in the repo only after all of them have copied.
13. **Output must be deterministic:** never show a time, a random value, a hash code, an identity, a thread name or a timing-dependent order. A timing demo (coroutines) compares a Boolean against a threshold with a wide margin (100 ms or more), never prints milliseconds. A claim in a note about a language behaviour must have been run or compiled, not remembered: a wrong note is worse than none (a lesson 3 note once said `var` + `MutableList` + `+=` is ambiguous; on Kotlin 2.4 it compiles and adds in place).

## Java module (`java-review/`)

14. **The Java module is the twin of the Kotlin one:** same rules 1-13, same priority marks, its own plan in `java-review/README.md` (lessons 0-18; some topics are Java-only: object contract, concurrency, modern Java). Substitutions: files are `.java`, one `public class` per file with `public static void main(String[] args)`, helpers are static methods of that class (so names only need to be unique inside the class, not the package), a model type shared by several files of a lesson gets its own file without `main`. The run class is `<package>.<ClassName>` (`mvn -q compile exec:java -Dmain.class=review.primitive.CharType`). Printing goes through `review.Output` (`java-review/src/main/java/review/Output.java`) with static imports by name, never a wildcard.
15. **`show` in Java:** `show(() -> expr);  // note` on ONE line, the note is the trailing `// comment`, text before `show` on the line is the printed code. Pairs for the templates: `syntax("form", "meaning", "form", "meaning")`, `bigO("op", "cost", ...)`. A lambda only captures effectively final locals, so compute a value that is reassigned into a new variable on its own line, then `show(() -> result)`. The type column is the run-time class, so an `int` prints as `Integer` (say so once per lesson that shows primitives).
16. **Exceptions are shown with `thrown`:** `show(() -> thrown(() -> Integer.parseInt("x")))` prints the exception class name (or "no exception"), also for Errors and checked exceptions; a stack trace in the output is a bug.
17. **Never write a backslash followed by `u` in a Java source file**, not even in a comment: javac reads it as a unicode escape and fails. Write `\\u` inside a string when the text itself is needed, and `(char) 1` for a control character. Prove every `wontCompile` with `javac` (`/d/_env_storeage/Java/jdk-21/bin/javac.exe` on this box) in a temp folder, the way Kotlin ones are proved with a scratch compile.

## TypeScript module (`typescript-review/`)

18. **The TypeScript module is the third twin:** same rules 1-13, same priority marks, its own plan in `typescript-review/README.md` (lessons 0-20; JavaScript-only topics: quirks, closures and `this`, the event loop). Substitutions: files are `.ts` in kebab-case with plain top-level code (no `main`), `import { ... } from "../output"` and nothing else (every file is self-contained: a file that prints must never be imported by another), `src/output.ts` is the helper. Run: `npx tsx src/<n>-<name>/<file>.ts` (`--plain` for ASCII). Typecheck a lesson folder: `bash scripts/check.sh src/<folder>` (strict mode, prints nothing when clean).
19. **`show` in TypeScript:** `show(() => expr);  // note` on ONE line, the note is the trailing `// comment`, text before `show` on the line is the printed code; templates are tuple pairs `syntax(["form", "meaning"], ...)`, `bigO(["op", "cost"], ...)`. Async results are awaited with top-level `await` outside `show`. Errors are shown with `thrown(() => ...)`, which prints the class name. The line parser tracks quotes and parentheses, so keep regex literals with quotes or unbalanced parentheses out of a `show` line. Event-loop and timer demos record the ORDER of events and never print time (rule 13).
20. **Prove `wontCompile` claims with `bash scripts/proof.sh <file.ts>`** (strict flags, prints the real tsc error codes); runtime-only behaviour is run, not remembered. tsc rejects some code JavaScript would run (`NaN === NaN`, `"5" * 2`): show the runtime value through a cast or `@ts-expect-error` and say so.
21. **Never delete files with `rm` plus a shell variable or a glob** (any module, any agent): Claude Code's critical-path guard asks the owner even in bypass-permissions mode and a background agent then waits for the answer. Use `mvn clean`, a new file name, or a literal path.
